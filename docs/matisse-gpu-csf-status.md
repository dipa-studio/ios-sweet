## 3. 已确立的事实（都有硬件证据）

1. **MCU 启动序列正确**：`MCU_CONTROL = MCU_CNTRL_AUTO(2)`，随后等全局中断。
   2372 实测 + 参考仓库 `kbase_csf_firmware_enable_mcu()` 源码双重确认。
2. **AS_MEMATTR 只在 2380 验证过厂商值，2391 没有用它**：厂商在 non-coherent SoC 上
   是 cached→索引 0、其余→索引 5、无 SH，值 `0x00084C8D888D8F88`；2380 回读确认过。
   但 2381–2391 的 manifest 都是 `csf_vendor_memattr=false`，实际用的是 shim 默认
   `0x4C4C9F4C/0x4C4C4C4C`（cached→索引 1）。叶子还带 nG（`0x800`），
   代码页因 `--ro-as-rw` 可写。详见 `docs/matisse-gpu-vendor-audit.md`。
3. **页表是对的**：2388 从 shim 实际交给 AS 的 arena 里读出 live leaf，
   `0x01000000→0x401a4000`、`0x01001000→0x401a5000`、`0x0100E000→0x401b2000`、
   `0x0100F000→0x401b3000`，同一张 L3 表四个相邻条目，flags 全为 `0xc47`。
   **没有过期条目、没有影子映射、没有第二张表。**
4. **未映射读的拒绝到达 MMU、不到达 MCU**：2384 故意读 `0x03000000`，
   得到 `AS_FAULT = 0x7cd002c2`、`AS_FAULT_LO = 0x03000000`，与 2375 读未映射堆时逐字节相同。
   **AS 拒绝在 MCU 侧表现为「事务永不完成」，不是会触发异常的总线错误。**
5. **reset 向量（VA 0x4）确实被使用**：2385 指向 `0x0100E001`、2389 指向 `0x01001001`，
   两处程序都被执行并写出标记。
6. **厂商入口 `0x010018ec` 可达**：2390 **向量字一个字节没动**，
   核写出了 `0x010018ec`。即**厂商固件在这里确实起步**，`version = 0` /
   `firmware_ready = 0` 表示「起步后挂住」，不表示「从未启动」。
7. **`0x01000200` / `0x01000600` / `0x01001200` 三个地址从未执行过**：
   无论是 reset 取指（2386/2387/2388）还是运行中 `bl` / 数据读（2373/2379/2382/2383），
   全部挂住、无异常。这三轮的 `cleanup_error = -53`，而成功的三轮为 `0`
   ——证明是真实的未启动，不是证据过期。
8. **2391：回退假说死亡，四个失败地址全是 512 字节对齐**。
   向量改到 `0x01001A01` 后，`0x1A00`（字面）、`0x1000`（页首）、`0x18EC`（厂商入口）
   三个落点都没有标记。若「非页对齐字被忽略→回退厂商入口」成立，`0x18EC` 应当写标记；
   它没有。同时，`0x200`/`0x600`/`0x1200`/`0x1A00` 四个失败目标全部是
   **512 字节对齐但不是 4 KB 对齐**，而 `0xE000`/`0x1000`（4 KB）和
   `0x18EC`（非 512 对齐）都能跑。
9. **2393：厂商页属性下 512 规则仍在，但还缺阳性对照**。
   leaf flags 回读 `0x4C3`（AttrIdx 0、无 nG、只读），与厂商完全一致；
   向量 `0x0100EA01` 指向 `0xEA00`，`0xEA00`/`0x1000`/`0x18EC` 三个落点都没有标记。
   说明 512 规则不是 shim 属性伪影。**但厂商属性下 `0xE000` 是否能启动尚未测**；
   在跑 2394 之前，不能排除“厂商属性编码本身让镜像起不来”。
10. **2394：厂商属性下 `0xE000` 能启动，`0xEA00` 不能——512 规则坐实**。
    2393 与 2394 用同一套厂商属性、同一容器布局，只把向量从 `0x0100EA01` 改到
    `0x0100E001`：`0xE000` 写出标记、`cleanup_error = 0`；`0xEA00` 无标记、
    `cleanup_error = -53`。这是同编码下的受控 A/B——512 对齐非页基不启动，
    不是属性伪影，也不是页/leaf 问题。

## 5. 还没回答的问题（按价值排序）

**A. 为什么 `0x200` / `0x600` / `0x1200` / `0x1A00` / `0xEA00` 不执行？**

**现象已压到最小，但机制仍未闭合。** 在 MCU 代码窗口
（VA `0x01000000`–`0x0100FFFF`）内，同一页、同一叶片、同一物理页里，
offset `0x000` 能读、offset `0x200` 挂；stack/shared 段里同样的 offset 模式能读。

叶片层面**已经榨干**，全部为空：

| 变量 | build | 结果 |
|---|---|---|
| 厂商叶片（AttrIdx 0/5、无 nG、只读、MemAttr） | 2393 | 仍挂 |
| 代码段非缓存 | 2395 | 仍挂 |
| 代码页可写（AP[2]） | 2378 | 仍挂 |
| shareability（SH） | 2374 | 仍挂 |
| 目标页 XN（PXN\|UXN） | 2397 | 仍挂 |
| memory group tag（bits 59..62） | 2398 | 仍挂 |
| 物理地址 bit 9 | 2396 | 排除：stack/shared 的读落在 PA bit9=1 上，都返回 |

`as_fault` 在成功侧和失败侧**都是 0**，故障入口也确认没有进过
（`group_stride` 保持 `0xa0`，不是故障桩写的 `0x14`），所以是真正的
"事务永不完成"。

**参照项目没有给出新变量**：x9（MT6993，CSF 已跑通）与我们的叶片编码、
MEMATTR、TRANSCFG、`MCU_CONTROL=2` 完全同构，差异都是平台层（SMMU bypass、
L2 上电、shader 委派），而厂商 MT6983 kbase 根本没有 iommu 代码；
OnePlus 的 MT6983 内核与小米版逐字节相同。

**剩下的问题不是"哪一位"，而是"这一位归哪一侧"**：任何页对齐映射都保持
`PA bit9 == VA bit9`，所以只有把**同一个失败 VA** 指向**一个已知可用的物理页**
才能分开。2399 就是这个实验。

**B. 向量是「按字面执行」还是「非页首时回退厂商入口」？**

**已回答：没有回退。** 2391 的三个落点同时布防，`0x1A00`（字面）和 `0x18EC`
（回退）都没有标记。2390 的 `0x18EC` 能跑，是因为厂商字本来就指向它。
剩下的二选一是「按字面走、在 `0x1A00` 挂住」还是「换掉厂商字后核直接不接受」；
2385/2389 换过字且能跑，说明换字本身不致命，所以“按字面”是唯一还在站着的读法。

**C. 厂商 handler 从 `0x010018ec` 起步后挂在哪里？**

**已定位到指令级，不需要新试验。** 2376 的未打补丁固件停在 cache helper 的第三条
字面量读：

```
0x010019d8  mov.w r1, #0
0x010019dc  ldr   r0, [pc, #0x1e4]    @ 0x01001BC4   <- 停在这里
0x010019de  str   r1, [r0]
0x010019e0  bx    lr
```

`0x01001BC4` 的 bit 9 = 1，与 2371/2373 测到挂住的读属于同一类；紧接着的两条
字面量 `0x01001BC8` / `0x01001BCC` 也是 bit 9 = 1。所以固件在完成 0x18EC→0x19DC
这段、并成功调用 `0x01003126` 之后，死在这里。**C 与 A 是同一个墙。**

**D. 为什么固件永远不 ready？**

大概率是 C 的直接后果，但尚未实测。

## 8. 如何继续（恢复点）

先读 `docs/matisse-gpu-mcu-wall.md` 第 40–46 节（第 40 节是旧规则，42–46 是五次收窄）。

1. **A 与 C 已合并**：入口不执行与数据读挂住是同一条规则，只出现在
   MCU 代码窗口内的 bit 9 = 1 地址。
2. **2395–2400 六次否定（已更正）**：缓存（取指方向 2395 / 数据方向 2400）、
   可执行性、memory group、物理页全部排除。**但 2396–2400 的阶梯把前两次
   读编码成了 `b<c>+movs`（`f8d4 0200` / `f8d6 0200`，而 `ldr.w` 应为
   `d4 f8 00 02`），所以“shared/stack 读返回”从未发生**；这些构建里唯一真正
   执行的读是 `0x01001200`。2399 唯一成立的事实是：把该页叶子指向 stack 页的
   物理页后读仍挂，因此墙不跟代码段自己的物理页走；它没有证明同一 PA 经
   stack VA 可读。
3. **2401 已飞（2026-11-07 23:25）——结论：墙不是代码窗口，是一个地址位**：
   `input_va = 1`、`groups = 8`、`as_fault = 0`、`mcu_status = 1`。阶梯确实从
   镜像的 `0x0300E000` 跑起来了（marker 1 落在 shared，别处不会写那个字），
   但**第一次读 shared `0x04000200` 就没返回**；没有 `0xE3`，故障入口未进入；
   读 2..6 从未发出。四个叶子与预测逐位一致
   （`0x30000000401a64c3 / 401a74c3 / 401b74c3 / 401b74c3`），镜像与 manifest 都真。
   `0x04000200` 的 **bit 9 = 1**。本系列所有返回过的访问 bit 9 全是 0
   （`0x01001900`、`0x02000000`、`0x02800000`、`0x0100E000`、`0x010018ec`），
   所有挂住的 bit 9 全是 1（`0x01000200`、`0x01001BC4`、`0x0100EA00`、
   `0x01001200`、`0x04000200`）。bit 9 在 4 KiB 页内偏移里，VA/PA 同位，
   所以换页永远分不开。**2401 自己的失误**：两个"对照"读都是 bit-9 = 1 地址，
   这轮走不到镜像那一半。
   下一步 **2402 已构建（bit-9 矩阵，待飞）**：去掉镜像，回到 2400 的布局，
   reset 字 `0x4 = 0x0100e001`，阶梯在 `0x0100E000`，六读 72 字节：
   `1 0x04000000` / `2 0x02000000` / `3 0x0100E400`（三个 bit9=0 必须先返回）、
   `4 0x0100E200`（同页，只差 bit 9，决定性）、`5 0x02000200` / `6 0x04000200`、
   `7` 全返回。顺序是设计的一部分：第一个挂死会截断阶梯，所以 bit9=1 的读
   全部排在后面；3 与 4 的地址偏移对称（`0x400`/`0x200`），既不是入口指令，
   也同页同叶同 PA。读 3 同时是 2373/2374「RX 冷行」假说的对照：它挂 → 墙是
   冷行填充，bit 9 出局；它返回 → 该假说与 bit 9 在同一枚镜像里分掉。
   镜像 `e7f00f28...e329`、内核 `ff842023...27ba`（`SWEET_BUILD_ID 0x2402`、
   补丁 0198）、arena `0x77000`、286 测试通过；preflight 已过，`boot_a` 仍是
   `2931647a...86b1`。
4. 每次仍按第 6 节链路：构建 → manifest/容器/ADT 校验 → runner → preflight →
   逐字确认 → 一次 `gpu-normal` → 恢复校验 → 解码 → 文档。

`0xEA00` 不跑），排除了属性伪影；厂商驱动没有这条约束，所以它是 MCU 硬件/固件
对 reset 向量的解释。下一步沿 `0x18EC` 的厂商 handler 布点，找它起步后停在哪。**

**更正（2399 之后）。** 上面第 9 节的一句话结论是 2393/2394 时期的写法，已被
2396–2399 连续收窄：墙不是 "512 对齐"、不是 reset 向量解释，而是 MCU 代码窗口
`0x01000000`–`0x0100FFFF` 内 **bit 9 = 1 的访问**；2399 又把物理页排除，说明
它跟着**虚拟区间**走。最新表述见 `docs/matisse-gpu-mcu-wall.md` 第 42、45 节。
