## 3. 已确立的事实（都有硬件证据）

1. **MCU 启动序列正确**：`MCU_CONTROL = MCU_CNTRL_AUTO(2)`，随后等全局中断。
   2372 实测 + 参考仓库 `kbase_csf_firmware_enable_mcu()` 源码双重确认。
2. **AS_MEMATTR 只在 2380 验证过厂商值，2391 没有用它**：厂商在 non-coherent SoC 上
   是 cached→索引 0、其余→索引 5、无 SH，值 `0x00084C8D888D8F88`；2380 回读确认过。
   但 2381–2391 的 manifest 都是 `csf_vendor_memattr=false`，实际用的是 shim 默认
   `0x4C4C9F4C/0x4C4C4C4C`（cached→索引 1）。叶子还带 nG（`0x800`），
   代码页因 `--ro-as-rw` 可写。详见 `docs/matisse-gpu-vendor-audit.md`。
3. **页表是对的**：2388 从 shim 实际交给 AS 的 arena 里读出 live leaf，
   `0x01000000→0x401a4000`、`0x01001000→0x401a5000`、`0x0100E000→0x401b2000`、
   `0x0100F000→0x401b3000`，同一张 L3 表四个相邻条目，flags 全为 `0xc47`。
   **没有过期条目、没有影子映射、没有第二张表。**
4. **未映射读的拒绝到达 MMU、不到达 MCU**：2384 故意读 `0x03000000`，
   得到 `AS_FAULT = 0x7cd002c2`、`AS_FAULT_LO = 0x03000000`，与 2375 读未映射堆时逐字节相同。
   **AS 拒绝在 MCU 侧表现为「事务永不完成」，不是会触发异常的总线错误。**
5. **reset 向量（VA 0x4）确实被使用**：2385 指向 `0x0100E001`、2389 指向 `0x01001001`，
   两处程序都被执行并写出标记。
6. **厂商入口 `0x010018ec` 可达**：2390 **向量字一个字节没动**，
   核写出了 `0x010018ec`。即**厂商固件在这里确实起步**，`version = 0` /
   `firmware_ready = 0` 表示「起步后挂住」，不表示「从未启动」。
7. **`0x01000200` / `0x01000600` / `0x01001200` 三个地址从未执行过**：
   无论是 reset 取指（2386/2387/2388）还是运行中 `bl` / 数据读（2373/2379/2382/2383），
   全部挂住、无异常。这三轮的 `cleanup_error = -53`，而成功的三轮为 `0`
   ——证明是真实的未启动，不是证据过期。
8. **2391：回退假说死亡，四个失败地址全是 512 字节对齐**。
   向量改到 `0x01001A01` 后，`0x1A00`（字面）、`0x1000`（页首）、`0x18EC`（厂商入口）
   三个落点都没有标记。若「非页对齐字被忽略→回退厂商入口」成立，`0x18EC` 应当写标记；
   它没有。同时，`0x200`/`0x600`/`0x1200`/`0x1A00` 四个失败目标全部是
   **512 字节对齐但不是 4 KB 对齐**，而 `0xE000`/`0x1000`（4 KB）和
   `0x18EC`（非 512 对齐）都能跑。
9. **2393：厂商页属性下 512 规则仍在，但还缺阳性对照**。
   leaf flags 回读 `0x4C3`（AttrIdx 0、无 nG、只读），与厂商完全一致；
   向量 `0x0100EA01` 指向 `0xEA00`，`0xEA00`/`0x1000`/`0x18EC` 三个落点都没有标记。
   说明 512 规则不是 shim 属性伪影。**但厂商属性下 `0xE000` 是否能启动尚未测**；
   在跑 2394 之前，不能排除“厂商属性编码本身让镜像起不来”。

## 5. 还没回答的问题（按价值排序）

**A. 为什么 `0x200` / `0x600` / `0x1200` / `0x1A00` 不执行？**

2391 之后，最好的单一解释是**reset 入口地址规则**：

> 目标是 512 字节对齐、但不是 4 KB 页基的地址时，核不启动；
> 4 KB 页基可以；不是 512 对齐的地址也可以。

| build | 目标 | 4 KB 对齐 | 512 对齐 | 结果 |
|---|---|---|---|---|
| 2385 | `0xE000` | 是 | 是 | 跑 |
| 2389 | `0x1000` | 是 | 是 | 跑 |
| 2390 | `0x18EC` | 否 | 否 | 跑 |
| 2386 | `0x200` | 否 | 是 | 不跑 |
| 2387 | `0x600` | 否 | 是 | 不跑 |
| 2388 | `0x1200` | 否 | 是 | 不跑 |
| 2391 | `0x1A00` | 否 | 是 | 不跑 |

**页 1 是受控样本**：`0x1000`（offset 0）、`0x1200`（0x200）、`0x18EC`（0x8EC）、
`0x1A00`（0xA00）在同一个 4 KB 页、同一个 leaf `0x401a5000`、同一组 flags `0xc47`。
两个跑、两个不跑，唯一分开它们的属性就是 offset 是否为 512 的倍数。

这是**拟合，不是受控实验**（成功行来自不同 build、不同向量字）。2392 要在
已知可执行的 `0xE000` 页里、offset `0xA00` 处重做一次，才能把“页/块”因素固定住。

**B. 向量是「按字面执行」还是「非页首时回退厂商入口」？**

**已回答：没有回退。** 2391 的三个落点同时布防，`0x1A00`（字面）和 `0x18EC`
（回退）都没有标记。2390 的 `0x18EC` 能跑，是因为厂商字本来就指向它。
剩下的二选一是「按字面走、在 `0x1A00` 挂住」还是「换掉厂商字后核直接不接受」；
2385/2389 换过字且能跑，说明换字本身不致命，所以“按字面”是唯一还在站着的读法。

**C. 厂商 handler 从 `0x010018ec` 起步后挂在哪里？**

仍是真正的目标。但 2391 把优先级改了：如果 512 字节规则是取指通路的性质，
厂商 handler 也可能挂在这条规则上。下一步仪器应**沿厂商代码路径记录它遇到的第一个
512 对齐取指目标**，而不是继续搬 reset 向量。

**D. 为什么固件永远不 ready？**

大概率是 C 的直接后果，但尚未实测。

## 6. 工程链路（怎么用）

```
改代码 → 内核 bump SWEET_BUILD_ID → build-xnu-local.sh
      → tools/matisse-shim-gpu-image.py --build-id 0x23xx … → 镜像 + manifest
      → research/.../shimXXXX-…-run-once.py preflight（只读）
      → 写 boot_a 前再次人工确认 → gpu-normal（写→启动→采证据→恢复→校验）
      → tools/matisse-gpu-report.py after-marks.bin --build 0x23xx 解码
```

关键约束：

- **必须 bump `SWEET_BUILD_ID`**（`xnu/out/local/xnu/bsd/dev/sweet_ufs.c`）。
  2385 忘了，marks 带的是 2384 编号；报告用 `--mark 0x23xx` 指定实际标记即可解码。
- **builder 参数是 `--kernel-sha256`**，不是 `--kernel-shasum`（旧文档笔误）。
- **raw 传输**：`tools/fbraw.py` 依赖 `pyusb`（已装 1.3.1）+ libusb。
  **fastboot CLI 在这个 LK 上会卡死**（`could not clear input pipe; e0005000`），不要走它。
- **恢复卡住先采证据**：`restore-only` 会在完整写回**之前**抓 `after` marks；
  恢复进 recovery 的是 stock 内核（不写 marks），证据不会被覆盖。
- **构建器拒绝覆盖已有输出目录**：有缺陷的产物归档为 `…-noleaf` 之类并写 NOTE.txt。
- leaf 属性与 shim 宏共用 `LEAF_PROBE_BUILDS`（0x2388–0x2391），有测试防止再次漂移。
- **补丁链已补齐 0183–0188**：2385 没有 identity（它的内核与 2384 逐字节相同），
  0183 直接从 `0x2384` 跳到 `0x2386`；0185 同时补上了 2388 的 leaf consumer。
  回放 0001–0188 与本地构建树逐字节一致。
