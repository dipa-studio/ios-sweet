## 2339：MCU 卡点定位（离线）

- 反汇编真实固件：VA 0 是标准 Cortex-M 向量表（SP=0x02040000，
  Reset=0x010018ed）。0x010018ec 确实是复位入口，2335/2336 没打错位置。
- 入口第 5/7 条指令先写外设 0x40022000=0xb、0x40022004=0x7，
  之后才碰私有内存。外设窗口不应答 → 总线挂死在第 5 条指令，
  完美解释“MCU_STATUS=1、无 fault、version=0、入口标记不出现”。
  也解释了 2334 为什么能跑：它的 20 字节自循环 stub 顺带跳过了这两个写。
- 2339 不替换任何指令，只改两个字面量（容器 0x281c/0x2820）指向
  shared+0xffc，把该字变成执行进度字：0=没跑，0xb=只跑第一条，0x7=两条都跑。
- 产物：kernel bbdfa95a、镜像 fb059ab3（27,119,616 B）。
  arena 锚点回到 0x77000（未编 entry probe），293 页，入口 offset 0xa8ec。

## 2340：MCU 确实在执行（重大转折）

- 一次授权试验，镜像 `4e801cc5`，`boot_a` 自动恢复 `2931647a`。
- **`version` 从 0 变成 `0xb`**，正是第一个 store（`0x010018f4`，
  r1=0xb，r0=0x04000000）写入的值。2339/2340 的 `csf_boot.o` 逐字节相同，
  唯一差别就是固件两个字面量 → 只能是 MCU 执行了那条 `str`。

  的入口检查点全在 `0xffc` → 它们读 0 未必是 MCU 没到，而是那个字不收写。

  `shared+4`（`features` 字段，ABI 不动）。判读：features=7 说明整页可写、
  只有 `0xffc` 坏；features=0 说明第二个 store 没执行。

## 2341：整页可写，只有 0xffc 是死字

- 一次授权试验，镜像 `3a098759`，`boot_a` 自动恢复 `2931647a`。
- `version=0xb` + `features=0x7`：两条入口 store 都执行，写进同页相邻两个字。
  → `shared+0` 和 `shared+4` 可写，`shared+0xffc` 不可写。
  **2335/2336/2337/2339 的入口检查点全在 0xffc，那些"未观测到"结论作废。**
- 反汇编确认真实外设 bit7 必为 0（`0x0302bc78`/`0x03800000` 都不在任何段，
  bit7 置起会让厂商固件自己取指失败），所以强制 r4=0 是复现硬件而非干扰。
- 入口完整反汇编：两条 store → SHCSR(0x70000) → PSP=0x0203F000 → control=2
  → 读 0x40003034 → `bl 0x01003126`(MPU 初始化) → 缓存失效/开启 I-cache
  → `b.w 0x01002aec`。栈 0x0203E000 已映射可写，push 不是问题。
- 已构建 2342（内核 `a22e9ef6`，镜像 `01a3905b`）：只把第二条 store 改到
  `shared+4`，真实 `0x40022000` 写与 `0x40003034` 读原样保留，全容器只改 3 字节。
  features=7 → 真实外设可用、卡点在后段；features=0 → 写 0x40022000 就挂。
- 208 测试通过。提交 `f3b1a62`。等用户对 2342 的 SHA 单独授权。
